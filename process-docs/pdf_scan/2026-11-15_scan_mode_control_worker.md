# 2026-11-15 - Scan mode for PDFs without a text layer (`extract` mode decision, control worker, `assemble` on `control.json`)

Worker branch `pdf-scan`. Builds on the tooling described in the area pdf_workflow. The skill `skills/websearch-pdf/SKILL.md` (user-owned) already described the scan flow before this work started and fixed the names `mode`, `control_pages`, `prompt_control.md` and `control.json`; everything else here was designed in this session and accepted by the orchestrator as proposed.

## Trigger

Until 2026-11-15 `extract` aborted with failure class `no_text_layer` when a PDF had fewer than 100 Latin alphanumeric characters per page on average. That gate was a tripwire from 2026-10-11, built when no PDF without a text layer had been observed. The first observed case: `2023-12-01 AR 139 Kley  Gedanken zur Zukunft des deutschen Governance Systems.pdf` (two spaces after "Kley"), 9 pages, producer "Microsoft: Print To PDF", `pdftotext` returns 9 bytes, liteparse without OCR returns 12 characters per page (nothing usable). So in scan mode liteparse is not run at all.

## Behaviour as built

- `extract` decides per PDF with the same criterion as the old gate (`MIN_TEXT_CHARS_PER_PAGE = 100`, average over the whole PDF) and writes `mode` into the start record and the manifest: `text` at or above 100 characters per page, `scan` below. A PDF has exactly one mode even if only some pages are scanned. Failure class `no_text_layer` no longer exists.
- `text` is unchanged: liteparse anchors, the four-template worker prompt, character recall in `assemble`.
- `scan`: same 50-page batches, one transcription worker per batch, prompt from `scan_worker_prompt.md` plus `scan_steps_single.md` or `scan_steps_split.md` with the shared `chunk_steps.md`. There is no anchor and no anchor file; the manifest entry has `anchor: null`. The prompt tells the worker the PDF has no text layer and the page images are the only source, and adds one rule the text prompt does not have: check numbers, dates, names twice against the image, write an unreadable character as `[?]`. Step numbering starts at 1 (the text prompt's step 1 is reading the anchor).
- Control draw: `draw_control_pages` draws `ceil(0.10 * pages_in_batch)` pages per batch with `random.Random(pdf_sha256)` and writes the sorted list as `control_pages` into the manifest. Observed values: 50-page batch 5 pages, 35-page batch 4, 9-page PDF 1, 1 000-page book 100. Seeding with the sha means a second `extract` of the same PDF draws the same pages (Kley always gets page 5). Chosen so that tests are hermetic without patching `random` and the draw needs no extra log field (the sha is in the start record).
- `prompt_control.md` (template `control_prompt.md` plus one `control_page_steps.md` block per control page) addresses one control worker for the whole PDF: step 1 reads every batch file that holds a control page, one step per control page reads the page image (pages parameter is the bare page number) and compares it with the text of that page in the named batch file, then one Write of `control.json`, then a one-line reply. The prompt fixes the JSON shape, the `kind` vocabulary (`missing_paragraph`, `misread_number`, `invented_text`, `broken_table`, `marker_missing`, `other`) and the meaning of `grave` (changes the meaning or loses content a reader needs). A missing page marker is to be reported as `marker_missing`, not grave, and the page is to be located by content; this follows from the observation in the area pdf_workflow that a marker can be lost while content is complete.
- `control.json` shape: `{"pdf": "<path>", "pages": [{"page": N, "batch": "batch_<from>-<to>.md", "correct": bool, "findings": [{"kind": ..., "grave": bool, "detail": "..."}]}]}`. `assemble` uses only `page` and `findings[].grave`; `correct` is informational and a grave finding wins over `correct: true`.
- `assemble` in scan mode: a batch is only checked for presence (`missing_file` fails exactly as in text mode, failure class `missing_batch`); no `pdftotext`, `chars_ref` 0, `char_ratio` null, `chars_out` still counted. Then `check_control`: no `control.json` gives `control_missing` (outcome `failed`); a drawn page absent from `pages` gives `control_incomplete` (outcome `failed`); at least one grave finding gives `control_grave` (outcome `content_check_failed`). Extra pages the worker checked beyond the draw are tolerated and counted in `control_checked`. On any failure nothing is written and the output names the missing pages and every grave finding as `page N grave: <kind>: <detail>`; on success every not-grave finding is named as `page N minor: ...`. End record fields in scan mode: `control_pages`, `control_checked`, `control_missing`, `control_grave`, `control_minor` (page lists).
- Tripwire: `control.json` that is not JSON or lacks `pages` or a `page` number raises `control_unreadable` (logged as the end record of the run, nothing written). Never observed; no test, per the rule that a tripwire needs no behaviour proof.
- A manifest without `mode` fails loudly (`KeyError`, logged as `assemble_error`); the first commit used `manifest.get("mode")` and silently treated such a manifest as text, the orchestrator rejected that in review. No manifest without `mode` was observed; all manifests written before 2026-11-15 lived in `/tmp` and are gone.
- `extract` cleans `control.json` together with its other patterns (`prompt_control.md` already matched `prompt_*.md`). The logged config gains `control_share` 0.10, `PROMPT_FILES` holds all nine templates, so `prompt_sha` and `config_hash` change with this build. `stats` needed no change: it only counts `failure_class`.

Shared names moved to `src/config.py`: `CONTROL_FILE_NAME`, `CONTROL_PROMPT_NAME`, `MODE_TEXT`, `MODE_SCAN`. A separate `control.py` module was considered and rejected: every control function is used by exactly one of `extract` and `assemble`, so each lives in its user.

## Limits, for a successor

- Control worker context (hypothesis, not observed): the control worker reads whole batch files. For a 1 000-page scan that is 20 files of about 50 pages each plus 100 page images, which probably exceeds the 1M window. The only observed scan has 9 pages and 1 batch. If a large scan appears, the control prompt needs a different read protocol (for example a `grep -n "<!-- page"` on the batch file followed by a Read with offset and limit); build it only when observed.
- A sample of one page (any PDF of 10 pages or fewer) is a weak check. The floor is `ceil` per batch; a larger minimum is one constant (`CONTROL_SHARE` or a floor next to it in `extract.py`).
- Whether Haiku reliably writes valid JSON without tool descriptions (see the area pdf_workflow on what Haiku workers receive) is answered once: the Kley control worker did. The `control_unreadable` tripwire covers the rest.
- The scan worker has no anchor, so the only check on its characters is the 10 percent sample. The text-mode recall check has no counterpart in scan mode by design; a per-page check is impossible without a reference.
- Seeding with the sha also means a redraw is impossible without changing the PDF or the code. If a retry should look at different pages, the seed has to include the `run_id` and be logged.
